SayQL includes an MCP server, so AI assistants like Claude and Cursor can query your databases through the connections you saved in SayQL.

On Linux, use the .deb or .rpm for MCP. The AppImage opens from a new folder each time, so the path you give your AI app would stop working.

The assistant can list connections, list databases, describe the schema, and run a read-only query. The same read-only rules apply. Database passwords are never shared with the assistant. What it gets back from a query is up to you, per connection (below): by default counts and summaries, not your rows.

It can also list your saved scripts (with their SQL on connections where you allow all rows, with string literals masked on counts and masked rows, and by name only where it may see nothing), and, on connections where you allow all rows, export a read-only query to a CSV in your Downloads folder (up to 100,000 rows). Exported rows aren't sent to the assistant, only the file path, but it could open the file, so export follows the same setting.

Three more tools hand work to you in SayQL instead of doing it:

  • Add connection opens SayQL's New connection dialog with the details filled in. You type the password in SayQL, test and save.
  • Open query opens SQL in a new SayQL tab, unrun. You review it and click Run; SayQL asks before anything that changes data, and the results stay in SayQL.
  • Open script opens one of your saved scripts, unrun.

The schema the assistant gets includes the database notes you saved, so it knows what codes mean and how tables relate.

Never-send columns

Columns you marked never send in a connection's agent settings stay private over MCP too, and describe_schema marks them [never sent to AI]. Write an entry as table.column for one table, or column for that column in every table. A query that could read one in any form is refused before it runs: naming it (also in WHERE, ORDER BY or COUNT), a whole row as one value (row_to_json(c), c::text), * inside a subquery or CTE, a column alias list, or a set operation that could rename it. When SayQL can't tell, it refuses and asks the assistant to name the columns it needs. A plain SELECT * runs, with those columns withheld.

On PostgreSQL, SayQL also asks the database for the query's plan first (EXPLAIN, which doesn't run it), so it follows views and renamed columns to the table they come from. On MySQL, SQL Server and SQLite it reads the SQL, so a view that renames a never-send column isn't followed: add the view's column to the list too. Functions defined in your database that read such a column aren't followed on any database.

Whatever the setting, AI apps can't call functions that read the server's files or reach outside the database (pg_read_file, pg_ls_dir, large objects, dblink, load_file, OPENROWSET, and the like), even when the saved login could. A login with only the rights it needs is still the best protection.

Table usage

After each table, describe_schema says how much it is used, from the database's own statistics, so the assistant can tell a live table from an abandoned one, for example usage: 12.3k reads, 0 writes, last write 2026-03-12. One line above the tables gives the period the figures cover ("since 2026-01-01", or "since the server started on …"): the counters reset when the server restarts or fails over, and differ on each replica. They are counts and dates, never row values.

  • PostgreSQL: reads (sequential and index scans), written rows and live rows from pg_stat_user_tables, and when the table was last analyzed; the period starts when the database's statistics were reset, else when the server started.
  • SQL Server: seeks, scans and lookups as reads, updates as writes, and the last read and write, from the index usage statistics since the server started. A table with no entry wasn't used in that time.
  • MySQL and MariaDB: read and write counts from performance_schema when it's on and readable, and the last write time MySQL keeps.
  • SQLite keeps no such statistics, so nothing is shown.

It's one extra query per describe_schema, stopped after 5 seconds. If the database user can't read the statistics (or they're turned off), one line says usage statistics are unavailable.

Notes suggested by AI apps

When an assistant learns a lasting fact about a database (a table that's no longer used and what replaced it, what a status code means, how two tables relate), it can call suggest_note with the note (up to 300 characters) and its evidence (up to 600), such as "no references in api/ since commit a1b2c3; usage: 0 writes since 2026-01-01". Notes describe the database, never the data in it: a note or evidence that looks like a value from your rows (an email, a phone number, a long id) is refused.

A suggestion isn't a note until you accept it. A database's suggestions show under Notes → Suggested by AI apps in the navigator, with a count; all of them are in Settings → AI apps → Suggestions, whose tab shows how many are waiting. The count is also on AI apps in the Settings sidebar and on the settings (gear) button, which opens straight to Suggestions while any are waiting. Each shows the app, the note and the evidence, with Accept (it's saved like a note you wrote, so the Ask box, agent mode and every AI app see it from then on) and Dismiss. Up to 50 suggestions wait per connection, a note already saved or suggested is refused, and each suggestion is in the agent activity log.

Passwords and writes never go through MCP. SayQL brings its window to the front and marks what came from an AI app, e.g. From Claude (MCP).

What AI apps may see

In Settings → AI apps → Access, the Connections table has a row per saved connection. Choose what an AI app gets back from a query under What AI apps get back:

  • Nothing: only how many rows a query returned, and its column names.
  • Counts and summaries (the default): the row count and, per column, its type, nulls and distinct values, and min and max only for a table's own number and date columns and for counts, sums, averages, minimums and maximums of them (not for computed expressions, which could carry text). No row values. The assistant answers with queries whose numbers answer the question, and can open SQL in SayQL when you want to see the rows yourself.
  • Rows, masked: rows, with likely personal data (emails, phones, names, IDs) replaced by tokens such as ‹email-1›. When a query moves values in a way SayQL can't trace to their column (UNION, VALUES, column alias lists, JSON access, functions in FROM), all its text is masked. This is best effort: a free-text column can hold anything.
  • All rows: rows as they are, in pages of 100 by default and at most 1,000, and CSV export. For data you're happy to share with that app.

Columns marked never send stay out at every level. They show as chips in the same row; Edit opens a list of your tables to pick them from (the same list agent mode uses, without turning agent mode on or off). Database errors can quote values, so below All rows (and at All rows for a query on a table with never-send columns) the assistant gets a fixed description of the error instead of the database's message: a syntax error and where, a column or table that doesn't exist (named only when the name is in its own SQL), a value that couldn't be converted, and so on.

These levels decide what SayQL sends back, and they keep your rows from reaching an AI app by accident. They don't make a determined agent harmless: a row count or a sum is a fact about your rows, and an agent set on it can turn a value into a count (WHERE email LIKE 'a%'). Never send is the firm line: SayQL refuses any query that could read those columns. For data an AI app must not learn at all, mark it never send, or leave the connection out.

Agent activity and blocking an app

The Activity tab lists what AI apps did through SayQL on this computer: when, which app, the connection, the SQL, and whether it ran (with the row count) or was refused and why. Filter it by app, by connection, or to refused queries only, and click a row to see its full SQL. Listing connections, databases and scripts, reading the schema, and handing work to you (with the SQL an app opened for you) are listed too. It keeps the SQL and counts, never rows: errors are kept only in their fixed form, and suggested notes wait in SayQL rather than in the log. The log is a file in SayQL's folder; Clear the log deletes it.

On the Access tab, Apps lists each app SayQL has seen, with whether it's allowed or blocked, when it was last seen and a Block button. A blocked app is refused everything until you click Allow. A block goes by the name the app reports when it connects, which nothing checks: it stops an app like Cursor, not software on your computer that reports another name, so it isn't a security boundary.

To keep out apps you haven't chosen, turn on Only allow apps I've approved at the top of Apps. Turning it on approves every app already listed that isn't blocked, so the apps you use now keep working. After that, an app you haven't approved is refused everything, logged as refused (not approved), and listed as Waiting for approval with Approve and Block; the app is told to ask you to approve it under Settings → AI apps → Access. A blocked app stays blocked even if it was approved. Approval goes by the reported name too, so it keeps out unknown apps but isn't a security boundary against software that lies about its name.

Hand-offs from an app SayQL doesn't recognise show its reported name marked (unverified).

If SayQL's settings for AI apps can't be read (a damaged file), every request is refused until you open SayQL, which shows the problem; the MCP server never moves or rewrites SayQL's files.

Set it up

Open Settings → AI apps and, on the Access tab, Connect an app (open by itself until an app has connected). It shows the exact command and config for your install:

  • Claude Code: run the claude mcp add command it shows, in a terminal.
  • Claude Desktop: merge the JSON it shows into claude_desktop_config.json and restart Claude Desktop.
  • Cursor and other MCP apps: add a stdio server that runs the sayql-mcp path from the Claude Desktop config shown in Settings.
