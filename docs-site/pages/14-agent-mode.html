Some questions need looking around before one query can answer them: "who owns this tenant?", "why did signups drop last week?", "is status 3 cancelled or refunded?". Investigate works through them in read-only steps and answers with the queries it ran.

Investigate was called agent mode before SayQL 0.4.9. Typing /agent still works.

Start an investigation

  • Switch the Ask box to Investigate (or press ⌘⇧A, or type /investigate), type your question and press ↵. With the box empty, it suggests a few questions to start with.
  • The agent first shows a short plan. Change any line, then press Go.
  • Auto mode: click Ask first next to the model name to switch to Auto, or press Go, and don't ask again on a plan. In Auto the agent doesn't stop for the plan or before each send; it still asks when a question has two meanings, and what it may see stays as the connection's setting. It applies to every tab until you switch it back.
  • Each step appears as it runs, with its SQL, row count and time. Click a step to see its rows in Results. Stop ends the run and the running query on the server.
  • When a question has two reasonable meanings, the agent asks you with choices instead of guessing.

The answer

  • Each sentence links to the steps it rests on. SayQL checks every number in the answer against the steps' results; a number it can't find is marked not verified.
  • The agent checks its joins: a join that repeats rows before they are summed is flagged, and the agent is told to fix it.
  • It never changes data. If the answer is a change, it shows the statement marked not run, with Open in editor; the usual confirmation applies when you run it.
  • Open as query, Save as script, Rerun (the same queries on fresh data, no AI) and Ask a follow-up work from the answer. To steer, open a step, choose Edit and continue, change its SQL, and the run continues from there.

Database notes

Notes are facts about a database that its schema can't tell, such as "the owner of a tenant is memberships.role = 'owner'" or "orders.status 3 = cancelled". They show under Notes in the Database Navigator (right-click to edit or delete), and the Ask box, Investigate and MCP apps all use them. A note can't hold values from your rows: one with an email, a number like a phone, or a masked value is refused.

At the end of a run the agent may suggest notes, and fixes to saved notes it found wrong. They show under the answer with Accept and Dismiss, and wait with the other suggestions under Notes → Suggested notes and fixes.

How notes stay true

Databases change. A note written about a column that has since been renamed would mislead the AI, so SayQL keeps each note tied to what it's about, and checks:

  • What a note is about. When you save a note, SayQL finds the tables and columns it names in the schema and remembers what they were like. The note dialog shows them.
  • When the schema changes. Before each question, at most once a minute, SayQL asks the database for a quick fingerprint of its schema (one small read-only query) and reads the schema again if it changed. It does the same right away when a query fails because a table or column doesn't exist. A note whose table or column was dropped, renamed or changed is marked may be out of date, with the reason, and SayQL suggests the fix: the note rewritten with the new name after a rename, or its removal after a drop. Nothing changes until you accept.
  • Checks. A note can have a check: read-only SQL that returns one row and one column, true while the note holds, such as SELECT count(*) = 0 FROM orders WHERE status NOT IN ('new', 'paid', 'cancelled'). SayQL runs it when the note is saved, when you open the database if it hasn't run for a week, when you click Check notes (the refresh button on the Notes row), and when Investigate asks. Only the answer, true or false, is kept. A check reads only and can't use never-send columns. A failing check marks the note may be out of date; a passing one shows as checked. Investigate, the audit and AI apps can suggest a check with a note.
  • What the AI is told. Only the notes about the tables in the question go with it. Each says how sure it is (checked 2 days ago, or may be out of date: the column orders.state no longer exists), and the AI is told that the schema wins when a note disagrees with it, and to check a doubtful note before relying on it.

A doubtful note shows a warning sign in the navigator, and a banner names it. Open it to see why, the suggested fix, its check and its earlier versions. Use the fix, edit the note, or choose It's still true.

What the AI sees

Investigate is off on every connection until you turn it on. The first /investigate on a connection asks what it may see of query results there (What the AI may see of query results); change it later with Change under the Ask box, or by right-clicking the connection and choosing Investigate settings. The choices use the same words as what AI apps get back, which is set separately; the dialog shows that one too.

SettingWhat the AI sees of each result
Nothing (names and row counts only), the defaultHow many rows it returned, and its column names. No values.
Counts and summariesThe row count and, per column, its type, nulls, distinct values, and min and max for a table's own number and date columns (and counts, sums and averages of them). No row values or group labels.
Rows, masked (up to 20 per query)Up to 20 rows. Likely personal data is replaced by tokens like ‹email-3› before it leaves; SayQL puts the real values back on your screen and into the SQL it runs.
  • Ask before each send pauses on exactly what would go, with Send and Skip (Skip sends the row count only). It starts on for cloud providers.
  • Never send columns are masked whatever the setting, and queries that could read them in any form (named, as a whole row, renamed in a subquery) are refused. Write table.column for one table or column for every table. The same list applies to AI apps over MCP (the dialog says so); the Ask box sends no values from your tables, so it doesn't need it. Database errors reach the AI as a fixed description, without the values they can quote.
  • Every step has a Sent to AI fold-out with the exact text that went to the model.
  • Masking is best effort. Columns are masked by name (email, phone, name, address, birth, SSN, MRN, patient, token, password, notes and similar) and values by shape (emails, phone numbers, card numbers, ID-like strings). A name in a free-text column with an ordinary name can get through, so for health or production data keep results at Nothing or Counts and summaries, or mark such columns never send.
  • With Ollama or LM Studio, nothing leaves your computer.

Safety and limits

Every agent query goes through the same read-only checks as the rest of SayQL, one statement at a time, and the database enforces read-only where it can. A query that would read all of a very large table without a filter is refused until the agent checks its plan. Each run has limits on steps, queries, time per query, time per run and tokens; change them in Settings → Investigate, where you can also pick the model that runs the agent (by default your expert model). Connect with a read-only database login for production.
