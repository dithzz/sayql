SayQL lets your team query production safely. Support, ops, PMs and analysts ask in plain English, without being SQL experts.

Get started

  1. Each person downloads SayQL and connects with their own login. SayQL connects straight from their computer; there's no SayQL server in between.
  2. Each picks an AI in Settings → AI provider, with their own API key or a local model.
  3. They ask: "orders for customer 4512 this month", "failed payments in the last hour", "signups per week since January".

Four layers of safety

  • Read-only by default. SayQL checks every statement before it runs.
  • Confirmation before any change. INSERT, UPDATE, DELETE, DDL and anything else that could change data stops and asks first.
  • The database enforces it. Reads run in a read-only transaction on PostgreSQL and MySQL, and on a read-only connection on SQLite, so the database itself refuses writes.
  • SQL Server has no read-only mode, so reads run in a transaction that's always rolled back. For production, give people a login that can only read (db_datareader).

The AI sees table and column names, types, keys, enum values and row estimates, never your table rows, unless you turn on Investigate for the connection. Results show up to 5,000 rows. For production, keep Investigate Off or at counts only, and connect with a read-only login.

AI agents on production

Claude Code, Cursor and other AI agents can query through SayQL too, under the same read-only rules:

  • On one computer: in Settings → AI apps, choose per connection what agents get back (the default is counts and summaries, not rows) and which columns are never sent. The Activity tab shows what each one ran, and you can block an app or let in only apps you approve. See MCP for AI apps.
  • For a team: on a SayQL server, give each agent its own key and only the databases, tables and rows it needs (for example orders where tenant_id = 42). Never-send columns are withheld on the server, and every agent query, refusals included, is in the audit log.
